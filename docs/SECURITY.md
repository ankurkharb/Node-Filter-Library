# Security Guide

Filtering is an API security boundary: query params are attacker-controlled input that selects columns,
operators and joins. This library is deny-by-default.

## Protections

| Threat                                                     | Protection                                                                                                                           | Tested in           |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------- |
| Filtering on an arbitrary column (`?password_hash=...`)    | Only declared filters are params; nothing is exposed automatically, and `filterFields` exposes only the names listed.                | `test/security`     |
| Reaching an undeclared relation (`?company__secret=...`)   | Relationship paths come only from configuration.                                                                                     | `test/security`     |
| Operator injection (`?age__$gt=`, `?age[gt]=`)             | Operators are chosen from your declared lookups; nested-object query values are dropped.                                             | `test/security`     |
| SQL injection                                              | Values are bound/escaped by Sequelize, including inside relationship subqueries, which are generated by Sequelize's query generator. | `test/security`     |
| LIKE wildcard injection (`?name__icontains=%`)             | `%`, `_`, `\` are escaped, as in Django.                                                                                             | unit + compat suite |
| Ordering by a sensitive column (`?ordering=password_hash`) | Only `orderingFields`; with none configured, clients cannot order.                                                                   | `test/security`     |
| Deep or costly joins                                       | `maxRelationshipDepth` (default 3), checked at startup.                                                                              | `test/security`     |
| Huge `IN` lists                                            | `maxInValues` (default 100).                                                                                                         | `test/security`     |
| Many filters / many search terms                           | `maxFilters` (50), `maxSearchTerms` (20).                                                                                            | `test/security`     |
| Expensive or invalid regex                                 | See below.                                                                                                                           | `test/security`     |
| A custom filter dropping another backend's restriction     | A filter `method` that removes or overwrites existing conditions throws `ConfigurationError`.                                        | `test/security`     |
| A configuration mistake turning into a client error        | `ConfigurationError` is not a `FilteringError`, so it is never mapped to a 400.                                                      | `test/security`     |

## Recommended configuration

```js
createFiltering({
  model: User, // validates everything at startup
  filterSet: UserFilterSet, // explicit filters; omit sensitive fields
  searchFields: ['username', 'email'],
  orderingFields: ['username', 'created_at'], // never '__all__' on models with sensitive columns
  defaultOrdering: ['-created_at', 'id'], // deterministic pagination
});
```

Also set a PostgreSQL `statement_timeout` for the API's database role. Every limit above bounds the
_shape_ of a query, but only the database can bound its run time.

## Regular expressions

`regex` / `iregex` lookups and `$` search fields let the client supply a pattern that PostgreSQL compiles.
Measurements on PostgreSQL 17 drove the checks:

- PostgreSQL's engine is not a backtracking engine for ordinary patterns: `(a+)+b` against 40,000
  characters runs in under a millisecond. The classic JavaScript ReDoS shapes are **not** a threat here,
  and they are allowed.
- The cost is in compiling **nested bounded repetition**: `(.{1,100}){1,100}` takes ~35 ms to compile,
  and `(a{1,255}){1,255}` fails with "regular expression is too complex".
- A repetition count over 255 is a PostgreSQL error.
- Back-references are the one construct that does make PostgreSQL backtrack.

So a pattern is rejected (HTTP 400) if it is longer than `regexMaxLength` (200), is not valid syntax,
contains a back-reference, has a repetition count over 255, or nests bounded repetitions whose product
exceeds 1000. DRF performs no checks, so the patterns rejected here reach PostgreSQL and return a 500
there. If you do not need client regexes, do not enable `regex` / `iregex` / `$`.

## Custom backends

- Take tenant or user identity from the authenticated request, never from a query param.
- Fail closed: if the identity is missing, match nothing (see
  [examples/custom-backend](../examples/custom-backend/TenantFilterBackend.js)).
- Add conditions with `andWhere`; never assign `queryState.where`.
- Put restricting backends first, so a later filter method cannot remove what they add.

## Errors

`FilteringError.toJSON()` includes the rejected `value`. That is useful to clients, but if your logging
treats error bodies as safe to store, remember they echo client input.
